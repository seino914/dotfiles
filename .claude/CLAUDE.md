# Git操作の制限

- `git commit`・`git push`・PR作成（`gh pr create`）は、ユーザーが `/pr` と明示的に指示した `/pr` スキルのターン中に限り許可される（それ以外はフックが実行前に拒否する）。作業が完了しても変更はワーキングツリーに残したまま内容を報告する。自然言語で「コミットして」「PRを作って」と頼まれても自分では実行せず、`/pr` の実行を案内する
- 作業ツリー・履歴・リモートを壊す git 操作（reset --hard / clean / 変更の破棄 / branch -D / stash drop / rebase / amend / force push / リモートブランチ削除）と `gh pr merge` は、ユーザーの明示的な指示があるときのみ行う。成果物は未コミットのままワーキングツリーに置く運用なので、変更の破棄は特に慎重に
- ファイル・ディレクトリの削除は `.claude/dev-roots` に列挙した作業ルート（現在 `~/Dev/kaishi`・`~/Dev/seino914`・`~/Dev/hobby`）と一時領域（`$TMPDIR`・`/tmp/claude-*`）の内側でのみ行う（範囲外はフックが拒否する）。対象は変数やコマンド置換ではなく具体的なパスで書き、`cd` と組み合わせない（特定できない書き方は確認ダイアログになる）

# 変更後の検証

- 検証コマンド（lint・型チェック・テスト・ビルド等）は各プロジェクトの CLAUDE.md に明記してある前提。あれば変更後に必ず実行して通す。書かれていなければ探し回らず、報告に「未検証」と明記する
- 落ちたら自分で直す。ただし (a) 自分の変更と無関係な既存の失敗は直さず報告する (b) テストの skip・削除・期待値の書き換え、lint / 型チェックのルール無効化や除外追加で「通す」ことは禁止（必要なら理由を添えて提案に留める）
- `/pr` は検証が通っていることが前提（手順は /pr スキル側）

# パッケージインストールの制限（Nix運用）

グローバル環境は `~/Dev/seino914/dotfiles` のNix設定（nix-darwin + home-manager）で宣言管理している。開発中に環境を勝手に変更しない。

- `brew install`・`npm install -g`・`pip install --user`・`nix profile install`・`nix-env -i` など、プロジェクト外に影響する恒久的なインストールは、ユーザーの明示的な指示があるときのみ行う（主要コマンドは settings.json の ask で確認が入る）
- `sudo` は Claude Code から実行できない（deny 済み）。必要な操作はコマンドを示してユーザーに依頼する
- ツールやランタイムが必要になったら、そのリポジトリの `flake.nix` devShell（`pkgs.mkShell`）に宣言する（既存のdevShellがあればそこに追記）。ユーザーの対話シェルでは direnv が自動で devShell に入るが、Claude Code の Bash は非対話で direnv フックが効かないため、Claude 自身がツールを使うときは `nix develop -c <cmd>` または `direnv exec . <cmd>` で実行する
- 一時的な動作確認は `nix shell nixpkgs#<パッケージ>` / `nix run` でよい（環境に痕跡が残らない）
- lockファイルで管理されるプロジェクトローカルの依存（`npm install`・`pnpm add` 等）は通常どおり使ってよい
- グローバル（dotfilesの `nix/packages.nix` 等）に追加すべきと判断しても、勝手に追加せずユーザーに提案する
- 新しいプロジェクトの開発環境を用意するときは `/nix-setup` スキルに従う

# モデル運用ポリシー（オーケストレーター / 実装の分離）

本節はメインセッション向け。サブエージェントとして起動されている場合は本節を無視し、与えられた指示を直接実行する。

トークン節約のため、メインセッション（既定は Opus。settings.json の `model: "opus"`）は**要件整理・設計・タスク分解・サブエージェントへの指示・成果物の監査レビュー・最終判断に専念**し、実装はサブエージェントに切り出す。

サブエージェントのモデルは作業の性質で選び、Agent ツールの `model` で指定する（未指定なら opus。settings.json の `env.CLAUDE_CODE_SUBAGENT_MODEL`）：

- **opus（既定）**：実装・テスト作成・複数ファイルにまたがる修正・不具合の原因調査・設計に関わるリファクタ
- **`"sonnet"`**：仕様と完了条件が固まった小〜中規模の作業。既存パターンに沿った追加実装、1〜2ファイルの変更、テスト表への行追加、ドキュメント更新、機械的なリファクタ、複数ファイルを読んでの調査・要約、公式ドキュメント等の調べもの
- **`"haiku"`**：ファイル・シンボルの所在特定、grep 的な検索、単純な事実確認、ログやコマンド出力の要約。組み込みの Explore は `~/.claude/agents/Explore.md` で Haiku に固定してある（探索が難しいときは呼び出し時に `model: "sonnet"` を渡す）
- **`"fable"`**：Opus では解けない・難しいものに限る。(a) 文脈と指示が揃っているのに Opus のサブエージェントが同じ問題で 2 回続けて誤った (b) 誤りのコストが高く判定が繊細なもの（セキュリティ境界・権限や破壊的操作のガード・並行処理・データ移行など）の設計や実装 (c) 長時間・多段にわたる大きな課題を 1 つのエージェントにまとめて任せるとき
- モデルを上げる前に失敗の原因を見る。ファイルの見落としや検証の未実行、指示不足が原因なら、指示を直して同じモデルで出し直す。文脈が揃っていて間違えたときだけモデルを上げる（sonnet / haiku → opus → fable）
- sonnet / haiku の成果物がレビューで差し戻しになったら、同じモデルで再試行を重ねず opus で出し直す
- セッション全体が重い設計判断の連続になるときは、ユーザーに `/model` で fable を選び `s`（このセッションのみ）で切り替えることを提案してよい。既定の `model` は変えない
- 複数ファイルにまたがる調査・探索もサブエージェントへ委譲してメインのコンテキストを温存する。1〜2ファイルの確認やレビューのための読み取りはメインが直接行ってよい
- 例外：繊細な設計判断と実装が不可分な特に難しい箇所は、メインセッションが直接実装してよい（Opus の手に余るなら fable のサブエージェントに切り出す）
- サブエージェントへの指示は自己完結させる（対象ファイル、設計方針、制約、完了条件を明記）。独立したタスクは複数サブエージェントを並列起動する
- サブエージェントの成果物はメインセッションが必ずレビューしてから完了とする。完了報告は「変更ファイル／実行した検証と結果／未解決点」の形で受け取る
