# Git操作の制限

- `git commit`・`git push`・PR の作成・更新（`gh pr create` / `gh pr new` / `gh pr edit`、`gh api` での `/pulls` への書き込み）は、ユーザーが `/pr` を実行したターン中だけ許可される（それ以外はフックが拒否する）。作業が済んでも変更はワーキングツリーに残して報告する。「コミットして」「PRを作って」と頼まれても自分では実行せず、`/pr` の実行を案内する
- 作業ツリー・履歴・リモートを壊す git 操作（reset --hard / clean / 変更の破棄 / branch -D / stash drop / rebase / amend / force push / リモートブランチ削除）と `gh pr merge` は、ユーザーの明示的な指示があるときのみ。成果物は未コミットで置く運用なので、変更の破棄は特に慎重に

# ファイル削除・プロセス停止

- ファイル・ディレクトリの削除は `.claude/dev-roots` の作業ルート（現在 `~/Dev/kaishi`・`~/Dev/seino914`・`~/Dev/hobby`）と一時領域（`$TMPDIR`・`/tmp/claude-*`）の内側で行う。範囲外の削除と、変数を含むパスの再帰削除はフックが確認ダイアログにする。ルート・ホーム直下の再帰削除・作業ルート自身・cwd・`~/.claude` とその実体の削除は拒否される。対象は具体的なパスで書く

# 変更後の検証

- 検証コマンド（lint・型チェック・テスト・ビルド等）はプロジェクトの CLAUDE.md にある前提。あれば変更後に必ず通す。無ければ探し回らず、報告に「未検証」と明記する
- 落ちたら自分で直す。ただし自分の変更と無関係な既存の失敗は直さず報告する。テストの skip・削除・期待値の書き換え、lint / 型チェックのルール無効化・除外追加で「通す」のは禁止（必要なら理由を添えて提案に留める）

# レビューの範囲

レビューする側（`/code-review`・レビュー用サブエージェント・セルフレビュー）にも、指摘を受けて直す側にも適用する。

- 指摘の前提は、その部品の脅威モデルで決める
  - **外部の入力・利用者に晒される部品**（API・Web 画面・認証認可・外部データのパースや保存・外部入力から組み立てるシェル / SQL / パス・秘密情報の扱い・権限境界）は、攻撃者がいる前提でレビューする。悪意ある入力による回避・注入・権限昇格は正当な指摘
  - **自分たち（ユーザーと Claude）だけが操作する部品の事故防止**（Claude Code のフック・開発用スクリプト・lint 補助などのヒューリスティックな検査）は、普通の使い方で起きる事故だけを見る。難読化（エスケープ・ブレース展開・引用符で割ったコマンド語・コメント細工など）や敵対的入力による回避は指摘しない（その防御は sandbox・権限の層の役目）
  - どちらか分からなければ、プロジェクトの CLAUDE.md の脅威モデルに従う。書かれていなければ「外部の入力が届くか」で判断する
- 指摘ごとに再現経路を 1 文で書く。事故防止なら「普通の使い方でどう起きるか」、セキュリティなら「攻撃者がどの入力を操作して何を得るか」。書けないものは出さない
- 次は指摘しない：現実に来ない規模・形の入力での性能。好みの問題。プロジェクトの CLAUDE.md / README に「対象外」「既知の制約」と書かれているもの
- 直す側は、指摘を「直す / 対象外」に仕分ける。対象外にしたものは、理由を一言添えて報告する。同じ部品に同種の指摘（抜け道・境界ケース）が 2 回続いたら、パッチを重ねるのをやめる。それは拒否するものを列挙するブラックリスト型の設計の限界の合図なので、次のどちらかをユーザーに提案する
  - セキュリティ境界：より強い仕組みへの設計変更（許可リスト型の検証・パラメータ化クエリ・フレームワークのエスケープ・sandbox など）。対象外にはしない
  - 事故防止の部品：対象外として明文化するか、設計を単純にする
- 修正後の再レビューは、修正した差分だけを対象にする

# パッケージインストールの制限（Nix運用）

グローバル環境は `~/Dev/seino914/dotfiles` の Nix 設定（nix-darwin + home-manager）で宣言管理している。開発中に環境を勝手に変えない。

- プロジェクト外に恒久的な影響が出るインストール（`brew install`・`npm install -g`・`pip install --user`・`nix profile install` 等）はユーザーの明示的な指示があるときのみ。グローバル（dotfiles の `nix/packages.nix` 等）への追加が要ると判断したら提案に留める
- `sudo` は実行できない。必要ならコマンドを示してユーザーに依頼する
- 必要なツールはそのリポジトリの `flake.nix` devShell に宣言する（既存の devShell があればそこに追記。新規プロジェクトは `/nix-setup` に従う）。Claude の Bash では direnv が効かないので `nix develop -c <cmd>` か `direnv exec . <cmd>` で実行する。一時的な確認は `nix shell nixpkgs#<pkg>` / `nix run` でよい
- lock ファイル管理のプロジェクトローカル依存（`npm install`・`pnpm add` 等）は通常どおり使ってよい

# モデル運用ポリシー（オーケストレーター / 実装の分離）

本節はメインセッション向け。サブエージェントとして起動されている場合は無視し、与えられた指示を直接実行する。

メイン（既定は Opus）は要件整理・設計・タスク分解・指示・レビュー・最終判断に専念し、実装はサブエージェントに切り出す。複数ファイルにまたがる調査も委譲する（1〜2 ファイルの確認やレビューの読み取りはメインが直接行ってよい）。繊細な設計判断と不可分な難所はメインが直接実装してよい（Opus の手に余るなら fable に切り出す）。

サブエージェントのモデルは Agent ツールの `model` で選ぶ（未指定なら opus）：

- **opus**：実装・テスト作成・複数ファイルの修正・不具合の原因調査・設計に関わるリファクタ
- **sonnet**：仕様と完了条件が固まった小〜中規模の作業（既存パターンに沿った追加、1〜2 ファイルの変更、テスト表への追加、ドキュメント更新、機械的なリファクタ、複数ファイルを読んでの調査・要約、公式ドキュメント等の調べもの）
- **haiku**：所在の特定・検索・単純な事実確認・出力の要約（Explore は Haiku 固定。難しい探索は `model: "sonnet"` を渡す）
- **fable**：Opus の手に余るものだけ。(a) 文脈が揃っているのに Opus が同じ問題で 2 回続けて誤った (b) 誤りのコストが高く判定が繊細なものの設計・実装（外部の入力に晒されるセキュリティ境界・並行処理・データ移行など。事故防止の部品は含まない）(c) 長く多段の大きな課題を 1 エージェントに任せるとき。セッション全体が重い設計判断続きなら、ユーザーに `/model` で fable を `s`（このセッションのみ）で選ぶよう提案してよい（既定の `model` は変えない）

運用：

- モデルを上げる前に失敗の原因を見る。見落とし・検証漏れ・指示不足なら指示を直して同じモデルで出し直し、文脈が揃っていて誤ったときだけ上げる（sonnet / haiku → opus → fable）。sonnet / haiku がレビューで差し戻しになったら opus で出し直す
- 指示は自己完結させる（対象ファイル・設計方針・制約・完了条件）。独立したタスクは並列起動する
- 成果物はメインが必ずレビューしてから完了とする。完了報告は「変更ファイル／実行した検証と結果／未解決点」の形で受け取る
- 挙動に関わる変更（コード・フック・設定。ドキュメントのみや数行の自明な修正は除く）は、完了とする前に新しいコンテキストのレビュー用サブエージェントに差分と要件だけを渡して独立レビューさせる。報告させるのは「レビューの範囲」節に当てはまる欠陥だけ。採否はメインが判断する
  - レビューは実装と別のモデルで行う（同じモデルは同じ見落としをしやすいため）。opus（メインの直接実装を含む）の実装は fable、fable の実装は opus、sonnet の実装は opus がレビューする
  - 外部の入力に晒されるセキュリティ境界は、opus と fable の 2 本を並列で独立にレビューさせる。指摘が食い違ったらメインが再現経路で判断し、決めきれなければユーザーに確認する

# 要約（compact）時に残すこと

要約時は次を必ず残す：

- 変更したファイルの一覧と、それぞれ検証済みか未検証か
- 実行した検証コマンドとその結果（失敗ならその内容）
- サブエージェントの担当・状態と未解決点
- ユーザーが確定した決定事項と、ユーザーの判断待ちの事項
