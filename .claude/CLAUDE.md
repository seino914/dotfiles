# Git操作の制限

- `git commit`・`git push`・PR の作成・更新（`gh pr create` / `gh pr new` / `gh pr edit` 等）は、ユーザーが `/pr` を実行したターン中だけ許可される（それ以外はフックが拒否する。サブコマンド直後に `--help` だけを置いた形と、`-u` 以外のオプションを伴わない `git push --dry-run` は対象外）。作業が済んでも変更はワーキングツリーに残して報告する。「コミットして」「PRを作って」と頼まれても自分では実行せず、`/pr` の実行を案内する
- 作業ツリー・履歴・リモートを壊す git 操作（reset --hard / clean / 変更の破棄 / branch -D / stash drop / rebase / amend / force push / リモートブランチ削除）と `gh pr merge` は、ユーザーの明示的な指示があるときのみ。成果物は未コミットで置く運用なので、変更の破棄は特に慎重に
- ファイル・ディレクトリの削除・移動は `.claude/dev-roots` の作業ルート（現在 `~/Dev/kaishi`・`~/Dev/seino914`・`~/Dev/hobby`）と一時領域（`$TMPDIR`・`/tmp/claude-*`）の内側だけ（範囲外はフックが拒否。一時領域の外の `/tmp` 配下は確認ダイアログ）。対象は具体的なパスで書き、変数・コマンド置換・`~user` を使わない（確認ダイアログになる）。`cd <リテラルのパス> && rm …` は cd 先を基準に判定されるので可だが、cd が 2 つ以上・サブシェル・`cd dir; rm …` / `cd dir && ls; rm …` のように cd から削除まで `&&` だけで結ばれていない形は確認になる。`bash -c '…'` は `nix develop -c` / `direnv exec .` / `env` / `timeout` 等を前に置いても中身で判定される
- 開発サーバー等の停止は `pkill` / `killall` ではなく `kill $(lsof -ti :<ポート>)` か PID 指定の `kill` で行う（名前指定の一括終了は確認ダイアログになる）

# 変更後の検証

- 検証コマンド（lint・型チェック・テスト・ビルド等）はプロジェクトの CLAUDE.md にある前提。あれば変更後に必ず通す。無ければ探し回らず、報告に「未検証」と明記する
- 落ちたら自分で直す。ただし自分の変更と無関係な既存の失敗は直さず報告する。テストの skip・削除・期待値の書き換え、lint / 型チェックのルール無効化・除外追加で「通す」のは禁止（必要なら理由を添えて提案に留める）

# パッケージインストールの制限（Nix運用）

グローバル環境は `~/Dev/seino914/dotfiles` の Nix 設定（nix-darwin + home-manager）で宣言管理している。開発中に環境を勝手に変えない。

- プロジェクト外に恒久的な影響が出るインストール（`brew install`・`npm install -g`・`pip install --user`・`nix profile install` 等）はユーザーの明示的な指示があるときのみ。グローバル（dotfiles の `nix/packages.nix` 等）への追加が要ると判断したら提案に留める
- `sudo` は実行できない。必要ならコマンドを示してユーザーに依頼する
- 必要なツールはそのリポジトリの `flake.nix` devShell に宣言する（既存の devShell があればそこに追記。新規プロジェクトは `/nix-setup` に従う）。Claude の Bash では direnv が効かないので `nix develop -c <cmd>` か `direnv exec . <cmd>` で実行する。一時的な確認は `nix shell nixpkgs#<pkg>` / `nix run` でよい
- lock ファイル管理のプロジェクトローカル依存（`npm install`・`pnpm add` 等）は通常どおり使ってよい

# モデル運用ポリシー（オーケストレーター / 実装の分離）

本節はメインセッション向け。サブエージェントとして起動されている場合は無視し、与えられた指示を直接実行する。

メイン（既定は Opus）は要件整理・設計・タスク分解・指示・レビュー・最終判断に専念し、実装はサブエージェントに切り出す。複数ファイルにまたがる調査も委譲する（1〜2 ファイルの確認やレビューの読み取りはメインが直接行ってよい）。繊細な設計判断と不可分な難所はメインが直接実装してよい（Opus の手に余るなら fable に切り出す）。

サブエージェントのモデルは Agent ツールの `model` で選ぶ（未指定なら opus）：

- **opus**：実装・テスト作成・複数ファイルの修正・不具合の原因調査・設計に関わるリファクタ
- **sonnet**：仕様と完了条件が固まった小〜中規模の作業（既存パターンに沿った追加、1〜2 ファイルの変更、テスト表への追加、ドキュメント更新、機械的なリファクタ、複数ファイルを読んでの調査・要約、公式ドキュメント等の調べもの）
- **haiku**：所在の特定・検索・単純な事実確認・出力の要約（Explore は Haiku 固定。難しい探索は `model: "sonnet"` を渡す）
- **fable**：Opus の手に余るものだけ。(a) 文脈が揃っているのに Opus が同じ問題で 2 回続けて誤った (b) 誤りのコストが高く判定が繊細なものの設計・実装（セキュリティ境界・権限や破壊的操作のガード・並行処理・データ移行など）(c) 長く多段の大きな課題を 1 エージェントに任せるとき。セッション全体が重い設計判断続きなら、ユーザーに `/model` で fable を `s`（このセッションのみ）で選ぶよう提案してよい（既定の `model` は変えない）

運用：

- モデルを上げる前に失敗の原因を見る。見落とし・検証漏れ・指示不足なら指示を直して同じモデルで出し直し、文脈が揃っていて誤ったときだけ上げる（sonnet / haiku → opus → fable）。sonnet / haiku がレビューで差し戻しになったら opus で出し直す
- 指示は自己完結させる（対象ファイル・設計方針・制約・完了条件）。独立したタスクは並列起動する
- 成果物はメインが必ずレビューしてから完了とする。完了報告は「変更ファイル／実行した検証と結果／未解決点」の形で受け取る
- 挙動に関わる変更（コード・フック・設定。ドキュメントのみや数行の自明な修正は除く）は、完了とする前に新しいコンテキストのレビュー用サブエージェント（opus、(b) は fable）に差分と要件だけを渡して独立レビューさせる。報告させるのは正しさと要件に関わる欠陥だけ。採否はメインが判断する

# 要約（compact）時に残すこと

要約時は次を必ず残す：

- 変更したファイルの一覧と、それぞれ検証済みか未検証か
- 実行した検証コマンドとその結果（失敗ならその内容）
- サブエージェントの担当・状態と未解決点
- ユーザーが確定した決定事項と、ユーザーの判断待ちの事項
