# Git操作の制限

- `git commit`・`git push`・PR の作成・更新（`gh pr create` / `gh pr new` / `gh pr edit`、`gh api` での `/pulls` への書き込み）は、ユーザーが `/pr` を実行したターン中だけ許可される（それ以外はフックが拒否する）。作業が済んでも変更はワーキングツリーに残して報告する。「コミットして」「PRを作って」と頼まれても自分では実行せず、`/pr` の実行を案内する

# ワークツリー

- 同時に走らせるサブエージェント同士が同じファイルを編集しうるときは、それぞれに `isolation: "worktree"` を付ける。触るファイルが重ならない・1 本だけ・読むだけの調査なら付けず、同じ作業ツリーで進める（ワークツリーごとにチェックアウトと依存の準備が要り、時間とディスクを使う）
- ただし、編集対象のファイルやそれが使うものに未コミットの変更があるタスク、gitignore 対象の場所（`docs/` 等）を読み書きするタスクには付けず、順番に進める（ワークツリーはコミット済みの HEAD から作られ、未コミットの変更も ignored のファイルも入らない）
- ワークツリーは標準の仕組み（サブエージェントの `isolation`・EnterWorktree・バックグラウンドセッションの自動分離）で `.claude/worktrees/` 配下に作る。`git worktree add` での手動作成は、ユーザーが求めたとき（既存ブランチの取り出し等）だけ（手動のものは自動掃除の対象外になり溜まる）
- 標準機能が自動で消すのは変更の無いワークツリーだけ。自分が起動したサブエージェントの `isolation: "worktree"` のワークツリーに変更が残ったら、ディスクを圧迫しないよう元の作業ツリーへ取り込んでから削除する。ユーザーへの確認は不要（結果に `worktreePath` / `worktreeBranch` が付く。複数あれば 1 つずつ順に）。EnterWorktree や `claude --worktree` などユーザーが求めたワークツリーは対象外で、指示があるまで残す：
  1. `git -C <ワークツリー> add -A`、`git -C <ワークツリー> diff --cached --binary --no-renames HEAD > <スクラッチパッド>/<名前>.patch`、起点として `git -C <ワークツリー> rev-parse HEAD` を控える。`git -C <ワークツリー> status --short --ignored` で ignored 側に作られた成果物（依存や生成物のディレクトリは除く）が無いかも見て、あれば別に取り込む
  2. 元の作業ツリーで `git apply --check <パッチ>` が通れば `git apply <パッチ>`（未コミットのまま置く。コミットは従来どおり `/pr`）
  3. 通らないファイルがあれば、それを `git apply --exclude=<パス> <パッチ>` で除いて残りを当て、除いたファイルは `git merge-file <元の作業ツリーのファイル> <起点の版> <ワークツリーの版>` で 3-way マージする（起点の版は `git show <起点>:<パス>` でスクラッチパッドへ取り出す。起点に無いファイルは空ファイルを起点にする）。衝突マーカーは両方のタスクの意図を残すよう解消し、残っていないことを確かめる。片側で削除・移動したファイルをもう片側で変更していたら、変更を移動先へ反映する（行き先が無ければ解消できないものとして扱う）
  4. すべて取り込んだら、元の作業ツリーで検証（テスト等）を通す（個別に通っていても組み合わせで落ちることがある）
  5. `git worktree remove --force <ワークツリー>` と `git branch -d <ブランチ>`（`--force` は取り込み済みの変更がワークツリー側にも残っているため）。`-d` が失敗したらブランチは残して報告に書く（ブランチはディスクを使わない）
  - 両タスクの意図が両立しない衝突や、両側で変更したバイナリなど解消できないものがあるときだけ、削除せずにワークツリーのパスと、取り込み済みのファイル・未解決のファイルを分けて報告する

# 変更後の検証

- 検証コマンド（lint・型チェック・テスト・ビルド等）はプロジェクトの CLAUDE.md にある前提。あれば変更後に必ず通す。無ければ探し回らず、報告に「未検証」と明記する
- 落ちたら自分で直す。ただし自分の変更と無関係な既存の失敗は直さず報告する。テストの skip・削除・期待値の書き換え、lint / 型チェックのルール無効化・除外追加で「通す」のは禁止（必要なら理由を添えて提案に留める）

# レビューの範囲

レビューする側（`/code-review`・レビュー用サブエージェント・セルフレビュー）にも、指摘を受けて直す側にも適用する。

- 指摘の前提は、その部品の脅威モデルで決める
  - **外部の入力・利用者に晒される部品**（API・Web 画面・認証認可・外部データのパースや保存・外部入力から組み立てるシェル / SQL / パス・秘密情報の扱い・権限境界）は、攻撃者がいる前提でレビューする。悪意ある入力による回避・注入・権限昇格は正当な指摘
  - **自分たち（ユーザーと Claude）だけが操作する部品の事故防止**（Claude Code のフック・開発用スクリプト・lint 補助などのヒューリスティックな検査）は、普通の使い方で起きる事故だけを見る。難読化（エスケープ・ブレース展開・引用符で割ったコマンド語・コメント細工など）や敵対的入力による回避は指摘しない（その防御は sandbox・権限の層の役目）
  - どちらか分からなければ、プロジェクトの CLAUDE.md の脅威モデルに従う。書かれていなければ「外部の入力が届くか」で判断する
- 指摘ごとに再現経路を 1 文で書く。事故防止なら「普通の使い方でどう起きるか」、セキュリティなら「攻撃者がどの入力を操作して何を得るか」。書けないものは出さない
- 次は指摘しない：現実に来ない規模・形の入力での性能。好みの問題。プロジェクトの CLAUDE.md / README に「対象外」「既知の制約」と書かれているもの
- 直す側は、指摘を「直す / 対象外」に仕分ける。対象外にしたものは、理由を一言添えて報告する。同じ部品に同種の指摘（抜け道・境界ケース）が 2 回続いたら、パッチを重ねるのをやめる。それは拒否するものを列挙するブラックリスト型の設計の限界の合図なので、次のどちらかをユーザーに提案する
  - セキュリティ境界：より強い仕組みへの設計変更（許可リスト型の検証・パラメータ化クエリ・フレームワークのエスケープ・sandbox など）。対象外にはしない
  - 事故防止の部品：対象外として明文化するか、設計を単純にする
- 修正後の再レビューは、修正した差分だけを対象にする

# モデル運用ポリシー（オーケストレーター / 実装の分離）

本節はメインセッション向け。サブエージェントとして起動されている場合は無視し、与えられた指示を直接実行する。

メイン（既定は Opus）は要件整理・設計・タスク分解・指示・レビュー・最終判断に専念し、実装はサブエージェントに切り出す。複数ファイルにまたがる調査も委譲する（1〜2 ファイルの確認やレビューの読み取りはメインが直接行ってよい）。繊細な設計判断と不可分な難所はメインが直接実装してよい（Opus が同じ問題で 2 回続けて誤ったら fable に切り出す）。

サブエージェントのモデルは Agent ツールの `model` で選ぶ（未指定なら opus。実装に出すときは `sonnet` を明示する）：

- **sonnet**：実装の既定。仕様と完了条件を固めてから渡す（既存パターンに沿った追加、複数ファイルの修正、テスト作成・テスト表への追加、ドキュメント更新、機械的なリファクタ、複数ファイルを読んでの調査・要約、公式ドキュメント等の調べもの）
- **opus**：仕様を固めきれない作業（不具合の原因調査・設計に関わるリファクタ）、sonnet がレビューで差し戻しになった作業の出し直し、独立レビュー
- **haiku**：所在の特定・検索・単純な事実確認・出力の要約。実装には使わない（差し戻しと再レビューで結局高くつくため）（Explore は Haiku 固定。難しい探索は `model: "sonnet"` を渡す）
- **fable**：消費が大きいので次の 2 つに限る。(a) 文脈が揃っているのに Opus が同じ問題で 2 回続けて誤った (b) 外部の入力に晒されるセキュリティ境界の設計・実装（事故防止の部品は含まない）。並行処理・データ移行・長く多段の課題も、まず opus で進めて (a) に当たったときだけ上げる。「重い」「大事そう」というだけで fable を選ばない

運用：

- モデルを上げる前に失敗の原因を見る。見落とし・検証漏れ・指示不足なら指示を直して同じモデルで出し直し、文脈が揃っていて誤ったときだけ上げる（sonnet / haiku → opus → fable）。sonnet / haiku がレビューで差し戻しになったら opus で出し直す
- 指示は自己完結させる（対象ファイル・設計方針・制約・完了条件）。独立したタスクは並列起動する
- 委譲は範囲を絞る：分かっている事実（調査済みの結果・対象ファイル・前提）は渡して再調査させない。調べものは問いを具体的に列挙し、確認できないものは深追いせず「確認できず」と書かせる
- 検索・事実確認・出力の要約・機械的な作業の委譲には Agent ツールで `effort: "medium"` を渡す（実装・原因調査・レビューは渡さず既定のまま）
- 成果物はメインが必ずレビューしてから完了とする。完了報告は「変更ファイル／実行した検証と結果／未解決点」の形で受け取る
- 挙動に関わる変更（コード・フック・設定。ドキュメントのみや数行の自明な修正は除く）は、完了とする前に新しいコンテキストのレビュー用サブエージェントに差分と要件だけを渡して独立レビューさせる。報告させるのは「レビューの範囲」節に当てはまる欠陥だけ。採否はメインが判断する
  - レビューは opus で行う（メインの直接実装・fable の実装も含む）。見落とし防止の主眼は、実装の経緯を知らない新しいコンテキストで見ること。fable でのレビューは次のセキュリティ境界に限る
  - 外部の入力に晒されるセキュリティ境界は、opus と fable の 2 本を並列で独立にレビューさせる。指摘が食い違ったらメインが再現経路で判断し、決めきれなければユーザーに確認する

# 要約（compact）時に残すこと

要約時は次を必ず残す：

- 変更したファイルの一覧と、それぞれ検証済みか未検証か
- 実行した検証コマンドとその結果（失敗ならその内容）
- サブエージェントの担当・状態と未解決点
- ユーザーが確定した決定事項と、ユーザーの判断待ちの事項
