# README更新・作成

プロジェクトのREADME.mdを、コードベースの現状に合わせて最新化する。存在しない場合は新規作成する。

## セクション構成

READMEは以下の順で構成する（更新・新規作成どちらの場合も）：

1. **概要**（必須）：何をするプロジェクトか1〜3文で
2. **技術スタック**（必須）：使用している言語・フレームワーク・主要ツール（パッケージ定義ファイルや設定ファイルから実際に確認できるもののみ）
3. **ディレクトリ構成**：主要なファイル・ディレクトリをツリー形式で。網羅は不要
4. **セットアップ**：インストール・初期設定の手順（実際に存在するコマンドのみ）
5. **コマンド**：利用可能なコマンド・スクリプト。カテゴリが2つ以上あるときはサブセクション（`###` 見出し）で入れ子にして整理する（例：`### 開発`、`### ビルド`、`### テスト`）

3〜5 は実態があるときのみ作る。書ける項目が1つ以下のセクションは作らず、憶測で埋めたり「該当なし」とだけ書いたりもせず、省いた理由を報告時にユーザーへ伝える。

## 言語

- 既存のREADMEがあればその言語に合わせる
- 新規作成時は、既存ドキュメント → コミットメッセージやコード内コメント → パッケージ定義の description の順に見て、プロジェクトの言語に合わせる。判断できなければ日本語（このユーザーの既定）。迷う場合は AskUserQuestion で確認する

## 手順

### 1. 現状把握

まずプロジェクトの実態を調査する：

- プロジェクトルートの `README.md` の有無を確認する（`Readme.md` や `readme.md` など別表記も探す）
- ディレクトリ構成を確認する（`ls` や Glob で主要なファイル・ディレクトリを把握）
- パッケージ定義ファイルを読む（`package.json`、`pyproject.toml`、`Cargo.toml`、`go.mod`、`Gemfile`、`flake.nix` など）：プロジェクト名・説明・スクリプト・依存関係を把握
- 直近のgit履歴を確認する（`git log --oneline -20`）：最近の変更内容を把握
- 設定ファイルやエントリーポイントを読み、セットアップ方法・実行方法を把握する

### 2A. READMEが存在する場合：更新

既存のREADMEを読み、実態との差分を洗い出して修正する：

- **実態と食い違っている記述**を修正する（削除されたファイルへの言及、変わったコマンド、古いファイル構成表など）
- **記載漏れ**を追加する（新しく追加された機能・ファイル・スクリプトで、READMEに載せるべきもの）
- **必須セクション（概要・技術スタック）が欠けていれば追加する**。既存の見出し名が近い意味であれば無理に改名しない
- **既存の構成・文体・見出しスタイルは維持する**。全面的な書き直しはしない。差分の修正に留める
- 手書きの説明文や意図的な記述は、実態と矛盾しない限り勝手に消さない

### 2B. READMEが存在しない場合：新規作成

調査結果をもとにREADME.mdを新規作成する。上記「セクション構成」を柱とする。

- 冒頭にプロジェクト名（`#` 見出し）を置き、その直下に概要を書く
- 実態から判断できない項目（ライセンス、デプロイ方法など）は書かない。憶測で埋めない

### 3. 報告

変更内容を簡潔に報告する：

- 更新の場合：何を修正・追加・削除したかを箇条書きで
- 新規作成の場合：どのセクションを作ったかと、実態から判断できず省いた項目があればそれも伝える

## 注意事項

- READMEに書くコマンドは、実際にリポジトリに存在するものだけにする。動作確認できない憶測のコマンドを書かない
- バッジ、絵文字の多用、誇張した宣伝文句は既存READMEにない限り追加しない
- コミット・push はしない（ユーザーが `/pr` を実行したときのみ）
